# 名片操作权限（替代企业认证）

本文件为当前规则，替代旧 `CARD_ACCESS_V2_SPEC.md`、`CARD_ACCESS_V2_PROGRESS.md` 及 agent.md 中的认证/审核测试描述。

## 两套身份

- 网页管理员保留独立账号密码与 `hq` / `company` 管理范围。
- 小程序三级权限只允许操作本人名片，不授予网页管理员身份，也不能访问别人的名片管理、收藏或数据。
- 一级：查看、转发、切换已有有效名片。
- 二级：在一个或多个指定企业下创建、编辑、换模板、删除自己的名片；模板必须由总部分配给目标企业。
- 三级：使用全部有效模板，为任意有效企业创建、编辑、换模板、删除自己的名片。
- 三级的样式列表与总管理员模板管理一致，每套模板仅展示一次；归属公司独立选择，切换公司不增加模板项。接口为每套模板返回 `companyOptions`，名片编辑页也据此提供公司选项。二级仍仅显示授权企业实际获配的模板。
- 后台新建、编辑、列表与导入说明统一使用“职业”（数据字段仍为 `title`）；不再显示“部门”输入框，历史部门数据保留，导入仍兼容“职位”“职务”表头。
- 名片来源不影响操作资格：管理员发放的名片同样受当前权限控制。
- 首页不单独显示新建按钮；有创建权限时从“名片样式”选择模板，再选择“新建名片”或“应用到当前名片”。当前卡无编辑权限时仍可进入样式页创建授权企业的名片；零名片账号保留首页首次创建入口。
- 降级只影响后续写操作，不停用既有名片和分享链接；下架由独立的名片删除/归档或账号停用操作完成。
- 企业认证页面和审核流程已移除，旧接口返回 410。旧 REVIEW_TEST_MODE 不再生效，reviewOnly 管理员不能登录，测试企业不再展示。

## 后台设置

进入“账号名片权限”，可按账号手机号添加待领取账号或匹配已有账号。

- 总管理员：给账号单独设置一级、二级（企业多选）、三级，或恢复默认。
- 子管理员：只给本企业设置二级权限或取消本企业二级权限，不改变其他企业授权。不能修改总部单独设置的权限或全企业权限。
- 子管理员列表只展示已关联本企业的账号；可用准确手机号添加成员，不开放全平台账号搜索。
- 已关联账号即使尚无名片或只有已归档/已删除名片，也继续显示在对应管理员的名片管理中。
- 角色/企业变化在下一次请求生效，后端对每次写操作重新校验。

## 默认策略

默认保持关闭，当前日常使用只依赖管理员单独授权：

```dotenv
MINIPROGRAM_DEFAULT_CARD_PERMISSION_ENABLED=false
```

此配置缺失时同样为 false。修改环境变量后需要重启后端。

- false：总管理员不显示默认策略表单；没有授权的账号均为一级。
- true：总管理员可在后台保存默认级别及二级企业范围，策略覆盖小程序注册、后台创建、批量导入的现有和新账号。
- 总部单独设置的 `person.cardPermission` 优先于默认策略；明确设置一级会阻止默认策略升级。
- 企业单独设置的 `person.companyCardPermissions[companyId]` 在默认一/二级基础上逐企业增减权限。
- “恢复默认”移除账号单独设置及企业覆盖，回到当前默认策略；开关关闭时回到一级。
- 默认策略保存在总部 `company_settings.data.defaultCardPermission`，不是写回 .env。
- 关闭开关不会清除单独授权，也不会归档已有名片。
- 原认证通过记录不转换为二级权限；原真实后台管理员身份不受影响。

## 微信审核体验入口

审核体验与已经删除的企业认证测试模式无关。该入口默认关闭，仅在微信审核期间按需开启：

```dotenv
WECHAT_REVIEW_ENTRY_ENABLED=false
WECHAT_REVIEW_CODE_HASH=
```

- `WECHAT_REVIEW_CODE_HASH` 只保存审核码的 64 位 SHA-256 哈希，不要把明文审核码写入代码、Git 或 `.env`。
- 可在本地用 Node.js 生成哈希：`node -e "console.log(require('crypto').createHash('sha256').update(process.argv[1]).digest('hex'))" "替换为临时审核码"`。
- 两项配置同时有效时，登录页才显示“微信审核体验”；修改服务器 `.env` 后需要重启后端。
- 审核账号固定为二级权限，只能操作隐藏的“微信审核演示企业”，可使用创大产控、晴空、蓝韵三套内置模板；初始演示名片使用创大产控模板。
- 每次输入正确审核码都会重置演示员工、名片、OCR 名片夹、浏览记录和旧会话，不接触正式员工、企业、模板或统计数据。
- 审核企业、员工和浏览数据不进入正式管理后台列表；审核账号不能登录管理后台、换绑手机号、切换账号或注销账号。
- 关闭开关或更换哈希后，已有审核会话在下一次请求时立即失效。审核结束后应关闭开关并重启后端。

## 数据与导入

权限字段保存在现有 people.data JSON 中，JSON 存储和 PostgreSQL 均复用现有接口，无需增加外部依赖或新表。

- `authPhone`：微信/短信验证过的登录手机号。
- `accountPhone`：管理员预建、导入待领取账号的匹配手机号。历史记录启动时一次回填，之后不会被名片联系电话覆盖。
- 批量导入的“手机号”同时作为账号手机号和新名片联系电话。
- 后台单独新建时分别填写账号手机号和名片联系电话，两者允许不同；后续编辑名片联系电话不会修改账号手机号。
- 导入按标准化账号手机号匹配；工号仅为历史兼容字段，不参与匹配、唯一性判断或账号 ID 生成。
- 导入或新增名片不会自动恢复已停用账号，恢复账号必须使用后台独立的“恢复账号”操作。
- 已注册账号保留 ID、openid、授权、收藏和浏览记录，导入只写对应企业名片。
- 重复导入同企业同模板更新原卡；后台“新建名片”可主动新增。
- 无手机号、格式错误、列表重复手机号、历史同号多账号均报告逐行错误；错误行不随意合并，正常行继续导入。
- 导入不会提升或清除权限。未注册账号之后用相同已验证手机号登录领取。

## 删除

员工端删除为 `lifecycle=deleted`，保留名片正文、deletedAt 和浏览记录。

- 原名片 ID 的公开页面、二维码、收藏详情及浏览写入均不可用。
- 当前名片删除后自动选择下一张有效卡，没有则显示空状态。
- deleted/archived 不占六张有效名片上限；启动迁移不能把 deleted 恢复为 active。
- 原模板重复导入不会复活已删除的名片 ID；新名片使用新 ID。
- 管理后台将已删除/归档卡显示为历史记录，不提供编辑入口。
- 总部合并重复员工时，源账号的名片和有效名片操作权限转移到保留账号，源账号停用并清空重复数据。

## 接口

- GET /api/card-permission-policy：管理员读取当前可见的策略和企业选项；子管理员不返回全局默认策略。
- PUT /api/card-permission-policy：仅总管理员且开关开启时，保存 `{level:1|2|3,companyIds:[]}`。
- GET /api/account-permissions?q=：按管理员企业范围列出账号及有效名片权限。
- POST /api/account-permissions：`{phone,level,companyIds}`，按手机号添加/匹配并授权。
- PUT /api/account-permissions/:id：单独设置权限；总部传 `level:null` 恢复默认。
- GET /api/employee/me：返回 permission、当前 canEdit 和逐卡 canEdit/canDelete；不展示已删除卡。
- GET /api/employee/templates：只返回当前名片权限允许使用的企业+模板组合。
- PUT /api/employee/me：检查当前企业和目标企业权限，支持 cardTemplate 修改当前模板。
- POST /api/employee/cards、DELETE /api/employee/cards/:id：检查企业名片权限；普通账号返回 403。
- PUT /api/employee/cards/active：一级账号仍可切换本人已有有效名片。
